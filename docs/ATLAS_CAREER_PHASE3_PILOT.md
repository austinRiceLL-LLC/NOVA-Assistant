# Atlas Career: Phase 3 pilot groundwork

This branch is stacked on the Phase 2 branch. It prepares a narrowly scoped application pilot, but **does not submit applications**. The default and only reachable state in this branch is disabled. There is no policy activation route, provider write adapter, employer credential, browser executor, scheduled run, or production deployment.

## Verified provider boundary

- Greenhouse Job Board GET endpoints are public; application POST requires an employer Job Board API key. Its documentation says the key must stay server-side and warns that its POST endpoint does not validate required fields. https://docs.greenhouse.io/job-board.html
- Lever's public postings are readable, but application POST requires an API key generated by that Lever account's administrator. Its documentation warns about rate limits and recommends the hosted form. https://github.com/lever/postings-api
- Ashby's public posting feed contains employer apply URLs. `applicationForm.submit` requires a key with `candidatesWrite` permission. https://developers.ashbyhq.com/docs/public-job-posting-api and https://developers.ashbyhq.com/reference/applicationformsubmit

An applicant's desire to automate applications does not grant these employer-controlled API permissions. Do not use candidate browser automation on sites that disallow it, and do not evade CAPTCHA, MFA, rate limits, or access controls. A user account restriction can never be ruled out completely.

## Added foundation

- `lib/career/apply-policy.ts` evaluates exact employer and HTTPS host allowlists, location and job class, annual USD salary, eligibility, current approved artifact, completed dry run, unresolved questions, one or two daily pilot slots, prior attempt, and a verified employer-authorized site capability. LinkedIn, Indeed, Handshake, and ZipRecruiter hosts are excluded from submission candidates.
- Provider responses are classified conservatively. Only an explicit confirmation ID can produce `submitted_confirmed`. A 2xx response without one or a 5xx response is `submitted_unverified`; 401/403/429 and provider blocks require review with no automatic retry.
- Migration `0004_plain_havok.sql` adds disabled-by-default controls, operator-only site capability metadata, one application record per user/job, and append-only application event storage. No UI or route can insert site capabilities or activate a policy.
- The authenticated `/api/career/pilot` route reports status and existing application records, and exposes only pause and disable mutations. The Career UI displays this status and links to two employer boards verified for discovery: Palantir's Lever board and Anduril's Greenhouse-linked careers page. Adding a board and running discovery still requires the user's action in the UI.

## Next gate for actual submission

1. Identify a specific employer that grants a documented applicant automation path or issues an authorized submission key, then verify its terms, credential scope, required form fields, and evidence response. Public job board access alone is insufficient.
2. Build that employer's adapter with mocked endpoint tests, server-only secret binding, form capability checks, and no bypass behavior.
3. Add an atomic reservation and daily-cap mechanism before any network POST. Reconcile ambiguous outcomes instead of blindly retrying. The unique user/job index is one layer of duplicate protection, not by itself an exactly-once guarantee.
4. Provide an explicit versioned standing policy UI and a tiny, user-approved live pilot quota. Apply migrations and deploy only after review.
